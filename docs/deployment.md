# Deploying Daedalus (Hetzner)

Daedalus runs on the same Hetzner box as Atlas and Icarus (`<server-ip>`,
user `agent`), as **two** systemd services — a trading loop and a
dashboard — mirroring Atlas/Icarus's worker+dashboard pattern. This is a
revision from the original single-service design; see "Why two services"
below for why.

## Layout

- Code: `/home/agent/daedalus` (git checkout of this repo)
- Venv: `/home/agent/daedalus/.venv`
- Secrets: `/home/agent/daedalus/.env` (mode `600`, owner `agent`)
- Data (event/trade JSONL history): `/home/agent/daedalus/data/`
- Trading loop unit: `/etc/systemd/system/daedalus.service`
- Dashboard unit: `/etc/systemd/system/daedalus-dashboard.service`
- Log rotation config: `/etc/logrotate.d/daedalus`

## Initial setup (already done as of this doc)

```bash
sudo -u agent git clone https://github.com/rhollandgreene-ctrl/alpaca-hackathon-agent.git /home/agent/daedalus
sudo -u agent python3 -m venv /home/agent/daedalus/.venv
sudo -u agent /home/agent/daedalus/.venv/bin/pip install -r /home/agent/daedalus/requirements.txt
```

`.env` was created with the correct key names and `REPLACE_ME` placeholder
values, `chmod 600`'d immediately, then filled in by hand over SSH — real
secrets were never generated by or passed through an assistant/chat session.

## Updating

```bash
cd /home/agent/daedalus
sudo -u agent git pull
sudo systemctl restart daedalus daedalus-dashboard
```

## Checking status

```bash
systemctl status daedalus daedalus-dashboard
journalctl -u daedalus -f            # trading loop logs (stdout/stderr)
journalctl -u daedalus-dashboard -f  # dashboard logs
tail -f /home/agent/daedalus/data/events.jsonl   # detected events
tail -f /home/agent/daedalus/data/trades.jsonl   # trade decisions/executions
```

Dashboard: **`http://<server-ip>:8506`**

## Why two services (revised from the original single-service design)

The original plan was one service: the trading loop, with the MCP server
as the only "dashboard," queried locally by an MCP client. That server
only works over **stdio** — it has no network listener at all — so once
Daedalus actually runs on Hetzner instead of a local machine, there is no
way to query it remotely. A Streamlit dashboard run as a second service
with `--server.address 0.0.0.0` is the same fix Atlas/Icarus already
apply for exactly this problem: a plain browser-reachable port, not
limited to whoever's SSH'd into the box.

This does **not** change the single-entry-point rule below. The dashboard
never calls `check_earnings()`/`check_macro_events()` and never touches
Tavily or yfinance — it only reads the same local `data/*.jsonl` files
(via `mcp_server/logic.py`, the same functions the MCP tools call) and
makes its own live Alpaca calls (`get_account()`, `get_all_positions()`)
for the account/position sections. It adds zero polling load to the
trading loop.

## The single entry point (trading loop only)

`daedalus.service` runs `python -m agent.options_executor` with no flags.
That module's `run()` loop calls `check_earnings()`/`check_macro_events()`
directly every `POLL_INTERVAL_SECONDS` (1800s) — it does **not** go through
`event_detector.py`'s own `run()`/`run_once()`. Do not additionally run
`event_detector.py` as its own standalone service: each `EventDetector`
instance keeps its own in-memory per-day Tavily cache, so a second process
polling earnings/macro data would double Tavily call volume for the same
watchlist with no benefit. (`daedalus-dashboard.service` does not run this
loop at all — see above.)

## Deliberate deviations from Atlas/Icarus

Atlas and Icarus were investigated first (see session history) so this
setup could mirror what already works and depart from it only where there
was a clear reason to. Differences, and why:

| Aspect | Atlas / Icarus | Daedalus | Why |
|---|---|---|---|
| Services | worker + dashboard pair (Streamlit) | same — worker + dashboard pair | Originally planned as one service (MCP server as the "dashboard"), revised once it became clear MCP's stdio-only transport can't be reached remotely off the local machine — see "Why two services" above |
| Deploy | manual edit-in-place on the server, no git | `git clone` once, `git pull` + restart to update | This repo already treats GitHub as source of truth, unlike Atlas/Icarus |
| `.env` permissions | Atlas `600`, Icarus `644` (inconsistent) | `600` | Mirrors Atlas's correct pattern; Icarus's `644` looks like an oversight, not intentional |
| `.env` provisioning | hand-created directly with real values | placeholder (`REPLACE_ME`) file created first, filled in by hand afterward | Real secrets never need to pass through an assistant/chat session at any point |
| Log rotation | none — `atlas.log`/`icarus.log` grow unbounded | `logrotate` from day one (`data/*.jsonl`, daily, 14-day retention, compressed) | Known gap in the existing pattern; no reason to inherit it |
| User | dedicated non-root `agent` (uid 1000) | same | No reason to deviate — already the right pattern |
| Unit shape | `Type=simple`, `EnvironmentFile=`, `Restart=on-failure`; worker `RestartSec=30`, dashboard `RestartSec=10` | same | No reason to deviate — already the right pattern |
| Dashboard auth | none — plain `--server.address 0.0.0.0`, no auth layer | same, deliberately | Agreed explicitly: matches the existing pattern rather than adding a layer Atlas/Icarus don't have |
